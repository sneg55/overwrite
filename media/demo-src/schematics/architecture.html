How it is put together

Three layers over one Canton participant. All ledger traffic goes through a single client, so every backend feature is testable in isolation with that client stubbed.

Webweb/src
/
Marketing page. Static server component: no ledger reads, no party session.
/app
The vault: epoch timeline, the written call, collateral locked, premium history.
/app/position
A depositor's own book, or the whole book for the operator.
/app/reports
Settlement history read off EpochReport contracts.
↓
Backendbackend/src
epoch-scheduler
Drives the lifecycle: open, lock, write, pay, settle, record, roll.
oracle-poller
Fetches public BTC spot and writes PriceObservation contracts.
mm-simulator
The buyer: takes the call, pays premium, exercises rationally at expiry.
rest-api
REST for the UI, through a ledger gateway.
ledger-client
The one shared seam to the ledger, alongside the CIP-56 registry adapter.
↓
Ledgerdaml/src
JSON Ledger API v2
Canton participant. Submissions and active-contract reads, per party.
package: overwrite
Nine templates: the vault, positions, the call, observations, receipts, reports.
CIP-56 token standard
Holdings, allocations and DvP. Collateral locks through this, never a bespoke lock.
CBTC registry
Devnet faucet plus the registry allocation surface. Mint and burn are never touched.
operator
Runs epochs and coordinates settlement. Real.
alice / bob / carol
Depositors. Real, funded from the devnet CBTC faucet.
mm-buyer
Buys the call and pays the premium.SIMULATED
oracle
Publishes BTC/USD. Self-operated, real spot data, labelled.
observer
Third party for the privacy reveal. Sees an empty ledger.

All demo parties are backend-owned and custodial. The party switcher in the UI is a demo control for reading the ledger from each party's perspective, not an auth boundary.
